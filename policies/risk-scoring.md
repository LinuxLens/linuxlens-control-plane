# Policy: risk scoring

**Status:** Binding  
**Applies to:** `linuxlens-assessment`, API aggregation, web, reporting

LinuxLens uses its own risk model. Raw CVSS MUST NOT be the displayed estate risk.

## Bands

| Score | Band | Meaning |
|---|---|---|
| 0–19 | Healthy | No material lifecycle, patch, or operational exposure |
| 20–39 | Watch | Drift or approaching milestones; routine work |
| 40–59 | Elevated | Remediation should be planned in the current cycle |
| 60–79 | High | Prompt remediation; material exposure or constraint |
| 80–100 | Critical | Immediate attention; unsupported, highly exposed, or operationally trapped risk |

## Composite host score

```text
linuxlens_risk =
    0.30 * vulnerability_exposure
  + 0.25 * lifecycle_exposure
  + 0.15 * patch_lag
  + 0.15 * operational_constraints
  + 0.10 * external_exposure
  + 0.05 * business_criticality
```

Each component is scored 0–100 by the corresponding file in `scoring/`. The composite is rounded to the nearest integer and clamped to 0–100.

Business criticality is a **declared** input (snapshot default: `standard` = 40). It amplifies priority; it does not invent technical exposure.

## Explainability

Every score MUST be reproducible from:

1. Collector evidence (or explicit `unknown` with penalty rules)
2. Knowledge records (lifecycle dates, support phases)
3. Declared business context
4. The scoring YAML in this repository

A finding’s narrative MAY be generated by an LLM only after the deterministic score and reasons exist. The model MUST NOT change the score.

## Unknowns

Missing evidence uses the `unknown` clauses in scoring YAML. Unknowns MUST be visible on the assessment (`coverage_gaps`) and MUST NOT be treated as Healthy.

## Estate aggregation

Estate roll-ups count hosts in each band. Estate “headline risk” is the count-weighted view, never the average of CVSS. Executive summaries MUST show band counts, not a single vanity number, unless that number is explicitly labelled as a derived metric.
